Short answer

Partly intrinsic, mostly self-inflicted. A much more resilient toolkit is plausible, though not one that never breaks.

  • Intrinsic: no Valve plugin ABI; stripped binaries rebuilt on nearly every update; engine interfaces change layout about monthly while their version strings stay the same; gameplay refactors.
  • Self-inflicted: engine vtable slots compiled in from a reverse-engineered header chain; first-match prologue signatures; hand-kept indices and offsets; cascading startup failures.
  • Proof point: build 26879581 (1.42.0.1) added one virtual to ISource2Server. CounterStrikeSharp crashes until an upstream SDK fix lands; a user's 8-byte binary patch already works around it. cs2kz was back in 3.5 h through a forked SDK. ModSharp's GameFrame detour is unaffected, but two of its JSON slot hooks shifted too, and fixing them is a data change, not a rebuild.
  • Feasibility (promising, small sample): on real breaking updates (Sep–Nov 2026), requiring two agreeing anchors healed 6 of 10 broken signatures and 6 of 6 moved vtable offsets with zero wrong answers; the rest went to a human. Accepting a single anchor was 20% silently wrong, and fuzzy byte matching failed outright. Not yet tested on an AnimGraph 2-scale update.

Intrinsic or self-inflicted?What any in-process addon must live with, and the seven choices that make today's stack fragile

Intrinsic to any in-process CS2 addon

  • No Valve plugin API or ABI. Every hook targets internal, non-exported code.
  • Stripped Linux binaries. On Source 1, symbol names made Linux signatures nearly immortal: TF2 had 0 Linux signature changes in 2025, and CS:GO went from 2–5 a year to 45 when its symbols were stripped in 2016.
  • The server module is rebuilt on nearly every update, so code shifts even when its source did not change.
  • Engine-interface layouts change about once a month, with unchanged version strings, so nothing reports the mismatch.
  • Engine-internal structs without reflection, and gameplay refactors that remove or rename fields and change behaviour.

Self-inflicted by today's stack

  • Binding engine interfaces through compiled C++ headers. One inserted virtual leaves the fix waiting on the upstream headers before CounterStrikeSharp can ship a release. It is rare (2 incidents) but has the slowest recovery, and it causes the current outage. Holding slot indices as data would turn it into a gamedata update.
  • Prologue-only signatures with first-match scanning. The ClientPrint signature currently binds to an unrelated constructor (#1494).
  • Hand-maintained vtable indices that move together and could be re-derived mechanically.
  • Hard-coded struct offsets in native and managed code, where schema lookup or an extracted displacement would do.
  • Cascading failures: native init stops at the first missing signature, taking unrelated features (game events, entity I/O, damage hooks) down with it. A broken managed signature becomes a null function that crashes on first call, and a missing schema field silently becomes offset 0.
  • No pipeline that tests new builds. Fixes start from user reports, ship partly untested, and need follow-up corrections in about 11 of 15 major breaks.
  • Gamedata updates that are unsigned, not keyed to the game build, and Windows-only.

Cadence is part of it, but not the whole story. CS2 ships about 1.7–3× as many patch versions per year as CS:GO did in 2017–22. CounterStrikeSharp needed a fix after about 11% of builds (20% with looser attribution), the same order of magnitude per year as SourceMod's CS:GO incidents. A per-build comparison was not computed, and SourceMod's counts include feature additions. The perception of constant breakage also comes from the slow header-chain fixes and from many plugins each carrying their own signatures.

A more resilient toolkit

  1. Loading: its own launch wrapper or server proxy, with no dependency on gameinfo.gi; cache everything per build ID.
  2. Resolver: several anchors per target (RTTI slot, unique string, caller plus ordinal, ConVar callback); accept an address only when two agree, and never take a first match.
  3. Engine interfaces: slot indices as data, verified at boot (RTTI vtable size, alignment against neighbouring slots); detour only functions with a unique body.
  4. Data: schema fields by name from the static tables; the few other offsets extracted from code and checked at boot.
  5. Linking: no mangled tier0 imports; dlsym with fallbacks; minimal own types.
  6. Failure: one feature switches off; the server keeps running.
  7. Pipeline: a Steam watcher archives each build, re-derives everything, smoke-tests a headless server and publishes signed gamedata.
  8. Plugin API: no raw offsets or SDK types; rename aliases; official surfaces where they fit.
Design details, residual breakage, and an incremental path for CounterStrikeSharpHow each piece works, what still needs a human, and changes CounterStrikeSharp could make without a rewrite

Every piece below already exists somewhere. SwiftlyS2 and ModSharp already combine several of them, but every stack still compiles in or hand-keeps engine slots, and only s2script checks them at boot (by vtable size). This is a design sketch, not a measured result, and all the binary analysis behind it is Linux-only; Windows/MSVC (identical-code folding, no frame pointers) is untested.

1. Loading

Load through a launch wrapper or a server-module proxy that finds engine init by a string reference, as SwiftlyS2 does, instead of depending on gameinfo.gi. Identify the build by steam.inf and the libserver.so build ID, and cache every resolved address per build ID.

2. A resolver instead of signatures

Each target is a declarative spec with several anchors: RTTI class and slot with a code fingerprint, unique strings, a caller with a unique string plus call ordinal, a ConCommand or ConVar callback, the VScript binding table, or the static schema tables. Accept an address only when two anchors agree, or one anchor plus a byte signature that matches exactly once (ModSharp's corroboration rule). Otherwise report the target as ambiguous; never take the first match.

3. Engine interfaces without compiled headers

Get interfaces through CreateInterface, whose names have been stable for three years. Keep slot indices as data, not compiled headers, and verify them at boot: compare RTTI vtable sizes and align each slot against its neighbours, using fingerprints that ignore line-number strings. Runtime fingerprinting alone is not enough: in CSource2Server 33 of 104 slots share a body with another slot (ApplyGameSettings is xor eax,eax; ret, the same as 8 others), and one shared ret body backs 16 vtable entries, so detouring it would hook all of them. Detour only unique bodies; otherwise patch the slot. Use small hand-written mirror classes only for slots proven stable, as Metamod's loader does with IAppSystem 0, 1 and 3.

4. Data access

Schema fields by name only, read from the static .data tables so they are available before the game initialises. For the few non-schema offsets, extract the displacement from an instruction inside an anchored accessor function, then assert it at boot with sanity checks such as slot ranges or a pointer back to the owning entity. A missing field raises an error; it never resolves to offset 0.

5. No fragile linking

Import no mangled C++ symbols from tier0. Look up the few needed C exports with dlsym and degrade if one is missing. Ship minimal own types (ModSharp's approach) instead of SDK templates whose inline code references engine globals.

6. Fail per feature, not per framework

Each resolved target backs a capability flag. Plugins can query it, the affected feature turns off with a clear log line, and the rest of the server keeps running. A boot self-test checks every binding before the first map loads.

7. Offline pipeline per build

Watch Steam every few minutes and archive each build as it ships: anonymous access only returns the current manifest, so old builds cannot be fetched later. Run headless analysis to re-derive every target and diff the vtables, then boot a dedicated server with bots and run the native test suite. Publish signed gamedata keyed by build ID, and send ambiguous targets to a human. S2GDU and s2script already do most of this, and s2script filed an issue 20 minutes after a build went public.

8. A stable plugin API

Plugins never see raw offsets, slots or SDK types. Generated schema bindings carry versioned rename aliases, and behaviour changes are absorbed by shims where possible. Categories that fit official surfaces (match management via logs and RCON, map logic via cs_script) can use those and never break.

Expected residual breakage (inferred)

Signatures, vfunc indices and interface slots account for most of CounterStrikeSharp's 383 gamedata changes and all of the header-chain rebuilds, and are mechanically re-derivable. Struct offsets, SDK refactors, schema rewrites and behaviour changes are roughly 40 incidents in three years, and some of them still need a human. The one auto-heal run covered a quiet span where every signature still worked, so it does not show what happens on a breaking update. The hoped-for outcome is CI handling most updates within an hour, a human stepping in every two to three months, and unresolved features disabled instead of crashing. That is unverified: proving it would mean replaying the pipeline across a structural build such as April 2026. S2GDU needs a headless IDA licence and is about 10 days old, and s2script's clean record covers only 4 builds.

Without starting over

CounterStrikeSharp could adopt much of this incrementally:

  • a uniqueness check in FindSignature
  • per-signature lazy resolution instead of one static initializer
  • an error, not offset 0, for missing schema fields
  • an RTTI cross-check of vtable offsets
  • resolving ISource2Server methods by fingerprint and detouring them, instead of KHook slot hooks from s2sdk
  • signed gamedata keyed by build ID on both operating systems
  • a CI job that boots each new build and runs the 180 native tests

Can the better stacks still be improved?

Yes, substantially. A code audit of ModSharp, SwiftlyS2, s2script and Plugify found that every one still compiles in or hand-keeps engine vtable slots, and build 26879581 hit all of them. s2script is the only one that noticed: its boot check disabled the affected hooks cleanly. The others hook the wrong functions silently. ModSharp's "Deactivated" hook now runs on the real Activated and tears down the Steam API context right after logon.

Seven gaps in the best stacksRuntime slot checks, two anchors everywhere, safe failure, reliable watchers, live smoke tests, build-keyed caches, several anchors per target
  1. Slot fingerprinting at runtime. No stack matches vtable slots against a stored baseline. s2script compares only the slot count, which an insert plus a removal would slip past.
  2. Two anchors everywhere. SwiftlyS2 and its loader take the first match. ModSharp votes on only about 4 of its ~30 vfunc resolvers, and outside debug builds its refs silently override a disagreeing signature.
  3. Sane failure. ModSharp kills the process on any missing entry. SwiftlyS2 calls a null pointer, or hooks slot 0 (the destructor) when an offset is missing. No stack gives plugins capability flags.
  4. Reliable watchers. s2script's 5-minute cron missed this build, SwiftlyS2's validator has been dormant since August, and ModSharp has none. A push trigger from Steam's product info service (Deadworks' model) beats cron.
  5. A smoke test on a live server. No stack boots a headless server on the new build in CI. s2script's PRs say "not live-tested", and Deadworks only checks that the code compiles.
  6. Missing everywhere: a resolve cache keyed by build ID, an archive of past binaries with slot history, signed gamedata, and Windows parity for the offline tooling.
  7. Several anchors per target. Valve rewording one string broke a ModSharp binding on Nov 12.

Inferred: combining these is mostly engineering, not research. The hard residue is the same as before: behaviour changes, schema rewrites, and the 25–30% of interface slots that are indistinguishable by body. The bigger obstacle is adoption: CounterStrikeSharp's ecosystem is 3–10× any other, so a new toolkit likely needs a CounterStrikeSharp-compatible API, or the fixes should go into CounterStrikeSharp itself.

ModSharp

It stands in for the server module and hooks only IAppSystem slots 0 and 3, which never move. It finds functions in order: VScript binding table, then refs (string, ConVar and vtable cross-references intersected, filtered by vtable membership), with a signature only to break ties. Of 178 address entries, 116 are signature-only, 47 have refs and 9 use VScript. Zydis-based resolvers re-derive vfunc indices and struct offsets from the instructions that use them, but most overwrite gamedata from a single derivation. GameFrame is a detour located by a ConVar, a game-system class and CSource2Server membership, so it survived. The Steam API hooks use hand indices 41 and 42, which moved to 42 and 43. Any failed entry ends the process with a forced minidump. Updates are manual commits, usually the same or next day.

SwiftlyS2

Its loader finds engine init by the first match of a startup string. Gamedata is fully hand-written (66 signatures, 131 offsets and indices). Signature scans take the first match. Hooks are vtable slots from offsets.jsonc, and schema fields resolve by hashed name in generated C#. A missing offset returns 0, so a hook lands on the destructor. For 1.42.0.1 the JSON fix landed in git at 03:39 UTC (67ef29b7), but the latest release predates it. S2GDU, the headless-IDA consensus tool, regenerates signatures and tracks slots by the nearest slot of compatible size. It needs a licensed IDA, publishes to a non-public repo and is not wired in yet.

s2script

Each interface has a pinned vtable size, checked against the live count at boot. On a mismatch, every hook on that interface is disabled and compiled engine calls return a miss value, with a banner at boot. Function finding runs signature, then resolve steps, then validators (prologue, string reference, vtable membership), and fails any entry that does not match exactly once. Its pipeline polls Steam every 5 minutes, aligns slots by fingerprint, regenerates schema and headers offline, and opens a PR from a Claude cloud session. For 26879581 the watcher missed the build; a human-triggered PR merged about 1 h 40 min after release, but shipping still needs a tag. It is Linux-only so far, and plugins get no runtime capability flags.

Plugify

Five ISource2Server hooks are compiled at the old slots. Its SDK fixed the header about 1.5 hours after the build, but the plugin has not been rebuilt, so the fix needs a binary release. Signature scans reject ambiguous matches, and init aborts on the first failed hook.

Deadworks (Deadlock)

Its mod database ingests each build within minutes. A workflow triggered by dispatch or a 30-minute cron regenerates schema, entity, ConVar and data bindings, compiles host, plugins and examples against them, and opens a PR listing what broke. Native signatures and vtable indices are still manual, and it is Windows-only.

Observations

  • 1.42.0.0 changed 456 schema entries but only 2 binaries and broke no one, which shows runtime schema resolution works.
  • 1.42.0.1 was a clean test of design: stacks with vtable slots in data files fixed it with a JSON edit (SwiftlyS2 GameFrame 19→20 in offsets.jsonc), while header-based stacks needed an SDK change and a rebuild.
  • Inferred: CounterStrikeSharp's fixes land 09:00–14:00 UTC the next day while Valve ships around 23:00 UTC, which fits a single maintainer's time zone.
  • Surface size confounds the ranking: s2script and cs2kz expose fewer signatures. But SwiftlyS2 has a large surface and still recovers about 5× faster than CounterStrikeSharp, so data-driven offsets and process explain part of the gap.
  • SwiftlyS2's "Game Sync" bot opens schema and protobuf regeneration PRs within about an hour of a build; s2script's bot reads new builds from Steam directly.
  • Standalone loaders (SwiftlyS2, ModSharp, Plugify, VoltMod) avoid Metamod but mostly reuse its gameinfo.gi trick. Metamod-based C++ stacks all wait on the upstream SDK when engine interfaces change.
  • Lock-in favours CounterStrikeSharp: its plugin ecosystem is 3–10× any other, hosting panels ship Metamod plus CounterStrikeSharp by default, and major plugins such as MatchZy exist only for it.

Recovery time

The main fix usually merges 12–34 hours after the first report (median about 23 h over 13 major breaks). One patch took about 6 days. In about 11 of 15 majors, corrections followed 1–8 days later; GiveNamedItem on Linux was re-fixed three times in six days. Fixes ship partly untested to cut downtime.

Repeat offenders

Offsets for Respawn (30 changes), CommitSuicide (29), Teleport and ChangeTeam (18 each). Signatures for PostThink (17), GiveNamedItem (16), SetModel, TerminateRound, SetPawn and TakeDamageOld (about 15 each). SwitchTeam, NetworkStateChanged and UTIL_Remove almost never break.

What resolves by name never breaks

Schema fields, net messages, game events, ConVars and RTTI lookups had zero value fixes in three years. They fail only when Valve renames or removes something. Every recurring break comes from bindings by position: byte patterns, slot numbers and struct offsets.

Fragility CSSharp adds itself

  • FindSignature takes the first match with no uniqueness check. In #1494 the Linux ClientPrint signature bound to an unrelated CNavBFSLattice constructor.
  • Failures cascade. Native init stops at the first missing signature (globals.cpp:129-157, entity_manager.cpp:63-110), so a missing FireOutputInternal also takes damage hooks and sounds down. On the managed side, a broken signature becomes a null function that likely crashes on first call; only a missing gamedata key throws TypeInitializationException in VirtualFunctions' static initializer. (Corrected: an earlier version said one broken signature disables all 19.)
  • A missing schema field returns offset 0 and is cached unchecked (schema.cpp:174,185). Inferred: reads and writes then hit the object's vtable pointer.
  • The auto-updater downloads a hand-maintained file over plain HTTP with no signature check, is not keyed to the game build, and has been Windows-only since 1f30e561. Inferred: only 3–4 of about 20 updates since 2024 could be fixed by gamedata alone.
  • The daily schema sync needs CSSharp to already load on the new build, so it trails the code fix by days.
  • The 180 native tests run only by hand inside a live server.
  • CSSharp depends on upstream s2sdk in lockstep: it forked twice, and #1502 is waiting on s2sdk PR #128.

Why a header change forces a rebuild

A virtual call compiles to [vtable + 8×N], with N fixed by declaration order. KHook and SourceHook read the slot from the member-function pointer at compile time. Struct offsets (CEntityInstance, ConVarData, Utl containers, CGlobalVarsBase, KeyValues3) are baked in too, and inline header code plus static SDK libraries import tier0 symbols directly. Every plugin built against the old headers is wrong until it is rebuilt.

A Game csgo/addons/metamod line in gameinfo.gi makes the engine load Metamod's loader as if it were libserver.so. What the binary looks like

libserver.so is stripped and built with GCC 14.2 (Steam Runtime 3) and the mold linker, not clang, as unity builds with frame pointers on. Only 21–24% of matched libserver functions (34% in libengine2) are byte-identical between consecutive builds, yet 99.5–99.8% are identical once RIP-relative and rel32 values are masked. Vtables and schema

Big updates move 6–11 of the 17 offsets at once (Jan 23 2026: 10 of 17; Apr 22 2026: 11 of 17), because one virtual added to a base class shifts every derived class. Schema field tables are static .data records (class name, size, count, then {name, type, offset} entries) and can be extracted offline: 948 classes and 6,774 fields, agreeing 5,160 of 5,160 with a runtime dump. Across the tracker dumps, 26% of consecutive builds moved some offset, sometimes thousands (2,269 fields and 301 class sizes in April 2026). Stable anchors

20.7% of functions reference a string and 6.9% reference a string no other function uses. 38.9% sit in a vtable. A unique string or vtable slot covers 44.5% of functions; one extra call hop covers 58.7%. ConCommands and ConVars are registered in static initializers, entity factories are static records and game event names are static pointer arrays. Example chain: string 13CCSPlayerPawn → typeinfo → vtable (416 slots) → slot 356, exactly where CounterStrikeSharp's PostThink signature lands.

Fuzzy matching fails. On 100 broken historical signatures with known current targets, abstracting operands found 1 correctly, abstracting registers found 0, mnemonics alone gave 0 (27 ambiguous, 62 wrong), and best-similarity gave 0 because the top scores all tied. GCC prologues are too uniform for loosened byte patterns to stay unique.

Valve shipped 8 CS2 server builds in 25 days (1.41.9.4 on Oct 30 to 1.42.0.1 on Nov 23). On the latest build CounterStrikeSharp is broken (#1502): Valve inserted one virtual into ISource2Server, so the GameFrame hook at slot 19 now lands on ApplyGameSettings and the server segfaults. The fix is waiting on s2sdk PR #128. cs2kz was running again in about 3.5 hours by pointing its submodule at a contributor's fork of the SDK.

Newer stacks bypass Metamod and the SDK headers

  • SwiftlyS2 loads through its own small server proxy (~500 lines) that finds engine init by a string reference. It uses s2binlib, a Rust library that reads the binary on disk: RTTI vtable lookup, string references, pattern scans.
  • ModSharp has its own loader and its own minimal headers, with no hl2sdk. Its gamedata has 49 "ref" entries that locate functions by string, ConVar or vtable membership. Its ResolveVote lets a runtime-resolved address override hand-written gamedata only when several anchors agree. A source comment says every past auto-resolve bug came from an uncorroborated guess.
  • ModSharp hooks GameFrame with an inline detour on the resolved function, not a vtable slot, so the 1.42.0.1 slot insertion does not affect it. Review correction: its gamedata hard-codes CSource2Server slot hooks for GameServerSteamAPIActivated (41) and Deactivated (42), and 41 moved to 42, so it is mis-hooked too, though the fix is a JSON edit. Its public mirror has no commits after Nov 12, so "no fix needed" cannot be confirmed.
  • ModSharp and CS2Fixes use Valve's leftover VScript binding table as a stable map from names to native functions.

Automatic regeneration now exists

  • S2GDU (Swiftly, started Nov 14): headless IDA. It re-finds each tracked function by voting over anchors (strings, ConVars, vtables, call chains, data pointers), regenerates the signature, re-derives vtable slots, and reports AMBIGUOUS instead of guessing. A chain of watchers detects each new Steam build and publishes gamedata for it automatically.
  • s2script polls Steam every 5 minutes. It aligns old and new vtables by instruction fingerprints per slot, so an inserted virtual shows up as Class[19]→20. It regenerates schema offsets offline and opens an issue plus an AI-written fix PR; one issue was filed 20 minutes after a build went public. It says plainly that a few non-schema struct offsets still need a live server test.
  • Deadworks (Deadlock): a build database that has every build within minutes, and a 30-minute cron that regenerates the API and checks that it compiles.

The cheat-side comparison

Offset dumpers such as cs2-dumper walk the interface registry and the schema system by name, which yields thousands of offsets without any byte pattern. They need only about 30 RIP-relative patterns for globals. Since 2025 they needed about 8 pattern fixes and one structural fix. They never handle function hooks, interface vtable slots, calling conventions or server behaviour, which are the main server-side break classes. Auto-healing is therefore easy for data offsets, moderate for globals, and hard for hooks, vtables and non-schema structs.

Valve's official surface: cs_script

Since about September 2025, maps can carry JavaScript run on V8 through a point_script entity. The API covers about 40 events (including OnModifyPlayerDamage and OnPlayerChat), entity spawning and inputs, GiveNamedItem, teleport, ConVars, ServerCommand, traces, a custom HUD and save data. It has no SteamID, networking, files or database, net messages, transmit control, usercmd access, econ items or generic hooks. It is bound to the map: there is no official way to load it server-wide, though Plugify and ModSharp inject one from native code. Valve keeps compatibility through deprecation shims rather than a frozen ABI.

Other official surfaces are RCON, HTTP log streaming (logaddress_add_http), GOTV broadcast and workshop collections. Game State Integration works only on the client. TMT2 runs MatchZy-style match management with no server plugin, using only logs and RCON. Inferred: roughly 40–60% of plugin categories could work this way at lower fidelity. Match management mostly fits, admin tools partly, DM, retakes and timers only through custom maps, and skins and anti-cheat not at all. Skin and knife plugins also break Valve's server-token rules.

No maintainer write-up blames link-time or profile-guided optimisation. The causes they document are vtable layouts compiled in from community headers, non-schema struct churn (about 45 layout commits after the July 2025 update), stripped binaries, behaviour changes, and a dependency chain that runs from the Valve build through s2sdk and Metamod to the framework and then the plugin.

CS2 does not update much more often than CS:GO did, and CounterStrikeSharp's gamedata breaks at roughly the rate SourceMod's CS:GO gamedata did. Three things are new in CS2: engine interfaces change far more often, Linux binaries carry no symbols, and every two to three months a large schema rewrite lands.

Cadence

GameTracking-CS2 has 416 builds (370 since launch): 92 in 2023 (from March), 111 in 2024, 106 in 2025 and 107 in 2026 up to Nov 23. The median gap is 2 days. CS:GO shipped 35–61 patch versions a year in 2017–22 (raw build counts are not in the data), so CS2 runs about 1.7–3 times faster by patch version.

How many builds actually break CounterStrikeSharp

65 hand-checked fix commits cluster into 39 incidents (4, 13, 12 and 10 for 2023–26). 38 of 361 builds since October 2023, about 11%, needed a gamedata or SDK fix (20% with looser attribution). Every structural build was followed by a fix within 1–3 days, as were Armory, 1.40.8.5, 1.41.7.7, 1.41.9.2 and 1.41.9.7. About half of major builds triggered fixes (12 of 25) against about 16% of minor ones. Each signature gets rewritten 1.5–2 times a year. Inferred: that incident rate matches SourceMod on CS:GO in its active years, so the feeling that everything breaks on every update comes mostly from SDK vtable churn and from many plugins each carrying their own signatures.

Symbols: the clearest Source 1 difference

On Linux, SourceMod could name functions by their mangled symbols (@_ZN…), which survive any recompile. CS:GO lost those symbols on 2016-11-28: SourceMod commit 6290834e2b swapped 12 symbol entries for byte patterns, nine fix commits followed within two days, and Linux signature changes went from 2–5 a year to 45, 34 and 14 in 2016–18. That jump is partly confounded: 64-bit Linux signatures were added in 2017, and Windows churn also rose in 2016. TF2 and CS:S kept their Linux symbols through their 64-bit ports; TF2's 2025 signature churn was 19 on Windows and 0 on Linux. CS2's libserver.so exports only CreateInterface, InstallSchemaBindings and a few metadata functions, and CounterStrikeSharp's gamedata has zero symbol entries.

Offsets dominate everywhere: in SourceMod 75–96% of changed keys are vtable indices or member offsets (TF2 2025: 482 of 503).

Interface versions did not protect CS:GO either

hl2sdk-csgo kept VEngineServer023, ServerGameDLL005 and VEngineCvar007 from 2012 while eiface.h was edited about 22 times for game updates. TF2 did bump ServerGameDLL in 2022. CS2's version strings are identical in samples from 1.38.6.0 (March 2023) to 1.42.0.1, while the cs2 eiface.h got about 40 vtable commits since late 2023: roughly 13 a year against about 2 for CS:GO. These are SDK commits, so they include reverse-engineering corrections as well as real Valve changes. The cs2 SDK branch gets 141–174 commits a year; csgo peaked at 44.

Rebuild behaviour

Depot manifests, tracked since 2026-10-04 (17 updates), show two modes. Game-only updates (7 of 17) change 1–4 Linux libraries, mainly libclient and libserver. Engine rebuilds change 11–33 of 60 Linux libraries and 50–56 of 102 Windows DLLs. libserver.so changed in 15 of 17 updates, including content-only ones; the only exceptions were client-only hotfixes. Inferred: the server module is rebuilt on essentially every server-side build, so raw offsets and fragile signatures drift even when the source did not change. Third-party libraries never change.
